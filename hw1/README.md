# ДЗ 1. Развертывание HDFS

Нужно поднять NameNode, SecondaryNameNode и 3 DataNode. Для начала возьмем
четыре VM с Ubuntu 24.04 и Java 11, как в среде курса. Hadoop будем использовать
версии 3.4.1. Установка будет в `~/mts-hdfs-hw1` у обычного пользователя,
то есть `sudo` для запуска скриптов не нужен.

## 1. Как разместим сервисы

Сделаем вот такое распределение:

| VM | Что запускаем |
|---|---|
| VM1 | NameNode |
| VM2 | DataNode и SecondaryNameNode |
| VM3 | DataNode |
| VM4 | DataNode |

NameNode хранит метаданные и знает, где лежат блоки файлов. Сами блоки хранятся
на DataNode. Поставим `dfs.replication=3`, тогда у каждого блока будет три копии,
то есть при работающих трех DataNode по одной на каждой.

SecondaryNameNode разместим на VM2, т.к. так его checkpoint будет храниться
отдельно от NameNode и нам хватит четырех VM. Он объединяет `fsimage`
и изменения из `edits` в новую контрольную точку. Заметим, что это не запасной
NameNode с автоматическим переключением при сбое, такую настройку тут не делаем.

## 2. Что нужно перед запуском

На каждой VM должны быть Bash, Java **11 JDK** (с утилитой `jps`), Python 3,
`curl`, `tar`, `sha512sum` и `timeout`. Также нужен доступ к `downloads.apache.org`
и `archive.apache.org`, потому что оттуда скачивается Hadoop. Для небольшого
стенда возьмем от 2 ГБ RAM и 5 ГБ свободного места на каждой VM.
На компьютере, с которого будем запускать скрипт, достаточно Bash и SSH.

Для начала проверим, что можем подключиться ко всем четырем VM по SSH-ключу.
При первом подключении через `ssh user@host` нужно сверить отпечаток ключа
сервера и сохранить его в `known_hosts`. Скрипт подключается без запроса пароля,
поэтому вход по ключу должен уже работать. Если нужны свой порт, отдельный ключ
или бастион, зададим их в `~/.ssh/config` и будем использовать SSH-алиасы.

Ключ остается на компьютере запуска. Копировать его на VM не нужно, т.к.
скрипт сам подключается к каждой машине и запускает на ней нужный процесс.

Ну и машины должны видеть друг друга по приватным IP. Вот какие TCP-порты
нужны внутри сети кластера:

| Порт | Где | Для чего |
|---|---|---|
| 9000 | VM1 | RPC NameNode |
| 9870 | VM1 | Веб-интерфейс NameNode и передача checkpoint |
| 9866 | VM2–VM4 | Чтение, запись и репликация блоков |
| 9867 | VM2–VM4 | IPC DataNode |
| 9864 | VM2–VM4 | Веб-интерфейс DataNode |
| 9868 | VM2 | Веб-интерфейс и HTTP SecondaryNameNode |

Эти порты открываем только в приватной сети, а SSH — со своего адреса.
В интернет HDFS не выставляем, потому что Kerberos здесь не настроен,
а одних прав на файлы недостаточно для проверки того, кто подключается.
Облачные правила доступа и firewall нужно настроить отдельно, скрипт их не меняет.

## 3. Как запустить

Сначала скопируем репозиторий и сделаем свой конфиг:

```bash
git clone https://github.com/krmoty/mts-data-platforms.git
cd mts-data-platforms/hw1
cp cluster.conf.example cluster.conf
```

Теперь в `cluster.conf` заменим `SSH_NODES` и `INTERNAL_IPS` своими адресами.
В обоих массивах порядок один и тот же: VM1, VM2, VM3, VM4.
В `SSH_NODES` можно указать публичные SSH-адреса или алиасы, а в `INTERNAL_IPS`
нужны четыре разных приватных IPv4-адреса, доступных со всех VM.
Сам `cluster.conf` в Git не попадает.

Ну и запустим:

```bash
./cluster.sh deploy
```

`cluster.sh` подключается к машинам по SSH и выполняет на них `node.sh`.
Сначала он проверяет зависимости и Java 11 на всех VM, затем останавливает
процессы этого стенда, если они уже были запущены. Дальше скачивает Hadoop,
проверяет SHA-512 и распаковывает архив. Если Hadoop уже установлен, повторно
скачивать его не будет. Основной источник — Apache Downloads, запасной — Apache Archive.

После этого скрипт записывает `core-site.xml`, `hdfs-site.xml`, `hadoop-env.sh`
и создает каталоги для данных, метаданных, checkpoint, PID и логов.
Адреса берет из нашего конфига, сервисы слушают приватные IP.
Проверка обратного DNS при регистрации DataNode отключена, т.к. для этих IP
может не быть PTR-записей. Период checkpoint поставлен 60 секунд, чтобы
при проверке не пришлось долго ждать.

Дальше нужно отформатировать NameNode. Это делается **только при первом запуске
с пустым каталогом**, потому что при повторном запуске нам нужно сохранить
старые данные. Затем запускаются NameNode, три DataNode и SecondaryNameNode.
В конце `deploy` сам вызывает проверку.

## 4. Как проверить, что все работает

Проверку можно запустить и отдельно:

```bash
./cluster.sh check
```

Для начала скрипт проверит процессы на всех VM и состояние DataNode через
JMX NameNode. Должно получиться `live=3`, `dead=0`, `stale=0`, `failed volumes=0`.
Потом дождется выхода из safe mode и выведет `hdfs dfsadmin -report`.

Теперь проверим сами данные: скрипт положит небольшой файл в `/hw1`, дождется
трех реплик, прочитает файл обратно и сравнит с исходным. То есть проверяем,
что данные действительно записались и читаются. В выводе `hdfs fsck` должны
быть `Status: HEALTHY` и `Live_repl=3`. Ну и отдельно проверяется, что
SecondaryNameNode создал файл checkpoint.

Если какая-то проверка не прошла, скрипт завершится с ненулевым кодом.
Результаты будут в локальной папке `results/`. Файл в HDFS оставляем, чтобы
можно было посмотреть его после перезапуска. При следующей проверке создается
новый файл с другим именем.

Можно также посмотреть состояние в браузере. Для этого откроем SSH-туннель,
подставив приватный IP VM1 и свой SSH-адрес:

```bash
ssh -N -L 9870:10.0.0.11:9870 ubuntu@vm1
```

Тогда по адресу [http://localhost:9870](http://localhost:9870) откроется
интерфейс NameNode. В **Datanodes** должны быть три живых узла без деградации,
в **Overview** — ноль missing/corrupt blocks. В **Utilities → Browse the file system**
можно открыть `/hw1` и увидеть тестовые файлы.

Если хочется выполнить команды вручную, подключимся к VM1 и запустим:

```bash
export HADOOP_HOME="$HOME/mts-hdfs-hw1/hadoop-3.4.1"
export HADOOP_CONF_DIR="$HOME/mts-hdfs-hw1/conf"
export PATH="$HADOOP_HOME/bin:$PATH"
hdfs dfsadmin -report
hdfs dfs -ls /hw1
hdfs fsck /hw1 -files -blocks -locations
```

Если что-то не запустилось, сначала посмотрим `.log` и `.out` нужного процесса
в `~/mts-hdfs-hw1/logs/` на соответствующей VM. Стоит проверить адреса, открытые
порты, версию Java и свободное место. После исправления можно снова вызвать `deploy`.

## 5. Как остановить и запустить заново

```bash
./cluster.sh stop
./cluster.sh deploy
```

`stop` останавливает процессы и сохраняет данные. При следующем `deploy`
NameNode заново не форматируется. Его метаданные отдельно удалять нельзя,
потому что после нового форматирования будет другой cluster ID, а на DataNode
останутся блоки старого кластера.

После перезагрузки VM тоже нужно вызвать `deploy`, т.к. автозапуск сервисов
при загрузке ОС здесь не настроен. При повторном запуске сохраняем прежние
каталоги и роли машин. На этом все :)

## Где проверялось решение

Проверка выполнялась в [GitHub Actions](https://github.com/krmoty/mts-data-platforms/actions/runs/38273291235):
четыре контейнера Ubuntu 24.04 с Java 11 внутри одной VM GitHub. Скрипты
подключались к ним по SSH. Проверены три реплики, чтение и запись,
создание checkpoint и повторное развертывание с сохранением старого файла.
Записи `RECEIVED SIGNAL 15: SIGTERM` в логах относятся к остановке процессов
при этой проверке перезапуска.

На учебных VM в MWS запуск не проводился. То есть работа скриптов проверена
на контейнерном стенде, а доступность адресов и настройки сети MWS нужно
проверить уже на самих VM.
